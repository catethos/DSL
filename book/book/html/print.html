DSL Documentation

Introduction

Welcome to the DSL documentation! DSL is a powerful Domain-Specific Language designed for building agentic LLM workflows, data processing pipelines, and integration systems.

What is DSL?

DSL is a modern, expressive language that combines:

  • Simple, readable syntax inspired by functional programming
  • Native LLM integration with multi-provider support (OpenAI, Anthropic, OpenRouter)
  • Powerful data processing with DuckDB integration and SQL support
  • Type-safe workflows with custom types and BAML integration
  • Rich ecosystem with multiple interfaces (CLI, TUI, Desktop GUI)
  • 50+ builtin functions for common operations

Quick Example

[1, 2, 3, 4, 5] as numbers

numbers |> sum(_)

"hello world" |> upper(_) |> split(_, " ")

type Person {
    name: String
    age: Int
    email: String
}

(1 || 2 || 3) as results

Installation

This guide will walk you through installing the DSL on your system.

Quick Install (Recommended)

The easiest way to install DSL is using our one-line installer:

curl -fsSL https://catethos.cloud:8000/install.sh | bash

That’s it! The installer will:

  • ✓ Detect your system architecture (x86_64 or aarch64)
  • ✓ Download the pre-compiled binaries
  • ✓ Install both dsl (terminal REPL) and dsl-gui (GUI interface)
  • ✓ Configure your PATH automatically

After installation, you can use either interface:

Terminal REPL:

dsl

GUI Interface:

dsl-gui

Verify installation:

dsl --version

No Rust Required!

Pre-built binaries mean you don’t need to install Rust or compile anything. Just run the installer and start using DSL immediately.

Two Interfaces Available

  • dsl - Terminal-based REPL with a polished TUI (Text User Interface)
  • dsl-gui - Native GUI built with egui for a graphical experience

Both interfaces provide the same DSL functionality. Choose whichever you prefer!

Optional: OpenAI API Key

For LLM-powered features, set your OpenAI API key:

export OPENAI_API_KEY="sk-..."

Tip

Add the API key to your shell profile (~/.bashrc, ~/.zshrc, etc.) to persist it across sessions.

Your First DSL Program

Let’s build a complete workflow from scratch. This tutorial walks you through creating a simple data processing pipeline.

Note: Comments Not Fully Supported

The examples below use # and // for documentation purposes. Comments are not yet fully implemented and may cause errors. When writing actual DSL code, avoid using comments until this feature is completed.

The Goal

We’ll create a program that:

  1. Creates a list of words
  2. Converts them to uppercase
  3. Joins them with a delimiter
  4. Gets the length of the result

Method 1: Step-by-Step in REPL

Press F1 to enter REPL mode, then type:

Step 1: Create Data

flow> ["hello", "world", "from", "dsl"] as words
✓ Bound 'words' to ["hello", "world", "from", "dsl"] : List

Step 2: Transform Data

flow> Map(words, Upper) as uppercase
✓ Bound 'uppercase' to ["HELLO", "WORLD", "FROM", "DSL"] : List

Step 3: Join Results

flow> Join(uppercase, " ") as message
✓ Bound 'message' to "HELLO WORLD FROM DSL" : String

Step 4: Get Length

flow> Length(message)
✓ 23 : Int

Success! You’ve created your first multi-step workflow.

Method 2: Using the Pipeline Operator

The pipeline operator |> makes this more elegant:

flow> ["hello", "world", "from", "dsl"]
    |> Map(_, Upper)
    |> Join(_, " ")
    |> Length(_)
✓ 23 : Int

Much better! The data flows left-to-right through transformations.

Method 3: Using Workspace Mode

For longer programs, use Workspace mode (F2):

  1. Press F2 to enter Workspace mode
  2. In the Editor pane, write:
def main() {
    let words = ["hello", "world", "from", "dsl"]
    let uppercase = Map(words, Upper)
    let message = Join(uppercase, " ")
    let length = Length(message)

    message
    length
}
main()
  1. Press Ctrl+R to run the program
  2. Switch to REPL pane (Tab) to see results

Complete Example: Data Analysis

Here’s a more practical example:

def main() {
    class Person {
        name: String
        age: Int
        city: String
    }

    let people = [
        Person { name: "Alice", age: 30, city: "NYC" },
        Person { name: "Bob", age: 25, city: "SF" },
        Person { name: "Charlie", age: 35, city: "NYC" }
    ]

    let nycPeople = filter(people, fn p => p.city == "NYC" end)

    let names = map(nycPeople, fn p => p.name end)

    let result = Join(names, " and ")
    result
}
main()

Note

This example uses higher-order functions like Filter and Map with anonymous functions.

Common Mistakes

Mistake 1: Forgetting Variable Binding

❌ Don’t do this:

["hello", "world"]
Map(_, Upper)

✅ Do this instead:

["hello", "world"] |> Map(_, Upper)
["hello", "world"] as words
Map(words, Upper)

Mistake 2: Wrong Function Arguments

❌ Don’t do this:

Join(" ", ["a", "b"])

✅ Do this instead:

Join(["a", "b"], " ")

Mistake 3: Missing Pipeline

❌ Don’t do this:

"hello" Upper

✅ Do this instead:

"hello" |> Upper(_)
Upper("hello")

Syntax Overview

The DSL provides a concise, expressive syntax for building AI-powered workflows.

Basic Structure

Expressions

Everything in DSL is an expression that evaluates to a value:

42
"hello"
[1, 2, 3]

Statements

Programs are composed of statements:

let x = 42
x + 10

Core Concepts

1. Values Are First-Class

Every expression produces a value:

flow> 42
✓ 42 : Int

flow> "hello" |> Upper
✓ "HELLO" : String

2. Variables Are Immutable

Once bound, variables cannot be reassigned:

let x = 42

Variables and Binding

Variables in DSL store values that can be referenced later in your program. DSL supports two equivalent syntaxes for variable binding.

Variable Binding Syntaxes

Syntax 1: Using as (Pipeline Style)

expression as variable_name

The as keyword binds the result of an expression to a variable name, flowing naturally in pipelines.

Examples:

42 as answer
"hello" as greeting
[1, 2, 3] as numbers

(10 + 5) as sum
Upper("hello") as uppercase

Syntax 2: Using let (Traditional Style)

let variable_name = expression

The let keyword uses traditional variable declaration syntax familiar to many programming languages.

Examples:

def main() {
    let answer = 42
    let greeting = "hello"
    let numbers = [1, 2, 3]

    let sum = 10 + 5
    let uppercase = Upper("hello")
}
main()

Both Are Equivalent

Note

Both as and let syntaxes compile to the same internal representation. Choose the style that feels most natural for your use case.

def main() {
    42 as x
    let x = 42

    "hello" |> Upper as result

    let result = Upper("hello")
}
main()

Variable Rules

1. Variables Are Immutable

Once a variable is bound, it cannot be reassigned:

let x = 42

Tip

Immutability prevents bugs and makes code easier to reason about. To “change” a value, create a new variable with a different name.

2. Variables Persist in Session

Variables remain available throughout your REPL session:

flow> 42 as x
✓ Bound 'x' to 42 : Int

flow> x + 10
✓ 52 : Int

flow> let y = x * 2
✓ Bound 'y' to 84 : Int

3. Naming Rules

Variable names must follow these rules:

  • Start with a letter or underscore (_)
  • Can contain letters, numbers, and underscores
  • Are case-sensitive
  • Cannot be keywords (let, as, if, else, fun, etc.)

Valid names:

def main() {
    let name = "Alice"
    let user_count = 10
    let _temp = 42
    let userID = 123
    let age2 = 25
}
main()

Invalid names:

def main() {
    let 2age = 25
    let user-count = 10
    let let = 42
}

Functions

Functions in DSL allow you to define reusable pieces of code. DSL supports both single-expression and multi-statement functions.

Defining Functions

Functions are defined using the def keyword:

def function_name(parameters) {
    body
}

Single-Expression Functions

The simplest function form contains a single expression that is automatically returned:

def double(x) { x * 2 }

def greet(name) { "Hello, ${name}!" }

def add(a, b) { a + b }

Using single-expression functions:

flow> def double(x) { x * 2 }

flow> double(5)
✓ 10 : Int

flow> double(21)
✓ 42 : Int

Multi-Statement Functions

Functions can contain multiple statements for complex logic:

def analyze_number(n) {
    let squared = n * n
    let cubed = squared * n
    let sum = squared + cubed

    {
        original: n,
        squared: squared,
        cubed: cubed,
        sum: sum
    }
}

Multi-statement rules:

  • Each statement is executed in sequence
  • Statements can be let bindings or expressions
  • The final expression is the return value
  • Semicolons between statements are optional but recommended
  • Intermediate variables are scoped to the function

Example:

def classify_value(value) {
    let abs_val = value < 0 ? -value : value
    let category = abs_val < 10 ? "small" :
                   abs_val < 100 ? "medium" : "large"

    {
        value: value,
        absolute: abs_val,
        category: category
    }
}

Scope Stack Implementation

DSL uses an efficient scope stack for variable management:

How It Works

  1. Global Scope (scope[0]): Never removed, persists across REPL sessions
  2. Function Scopes: Created when functions are called, removed when they return
  3. Variable Lookup: Searches from innermost (current) to outermost (global) scope
  4. Variable Binding: Always creates variables in the current scope

Performance Benefits

Control Flow

Control flow in DSL allows you to make decisions, branch execution, and handle different cases in your programs.

Conditional Expressions

The Ternary Operator ?:

The most common way to branch in DSL is using the ternary conditional operator:

condition ? true_expression : false_expression

Basic Example:

let age = 25
age >= 18 ? "adult" : "minor"

Chained Conditionals

For multiple conditions, chain ternary operators:

score >= 90 ? "A" :
score >= 80 ? "B" :
score >= 70 ? "C" :
score >= 60 ? "D" : "F"

Conditionals with Variables

    let weather = temperature > 80 ? "hot" :
                  temperature > 60 ? "warm" :
                  temperature > 40 ? "cool" : "cold"

    weather
}

In Pipelines

Conditionals work seamlessly in pipelines:

[1, 2, 3, 4, 5]
|> Length
|> (_ > 3 ? "many items" : "few items")

Multi-Statement Conditional Branches

For conditionals that need multiple statements, use blocks within the ternary operator:

def main() {
    let x = 10

    x > 5 ? {
        let doubled = x * 2
        let message = "Greater than 5: ${doubled}"
        message
    } : {
        let message = "Not greater than 5"
        message
    }
}
main()

In Functions

Functions can use ternary operators for conditional logic:

def classify_age(age) {
    age < 13 ? "child" :
    age < 20 ? "teenager" :
    age < 65 ? "adult" : "senior"
}

classify_age(25)

Or use match expressions for clearer multi-case handling:

def classify_age(age) {
    match age {
        a if a < 13 => "child"
        a if a < 20 => "teenager"
        a if a < 65 => "adult"
        _ => "senior"
    }
}

AND Operator &&

Both conditions must be true:

    let age = 25
    let verified = true

}
main()

At least one condition must be true:

    let is_admin = false
    let is_owner = true

    is_admin || is_owner ? "can edit" : "read only"
}
main()

NOT Operator !

Negates a boolean value:

let is_logged_out = false

!is_logged_out ? "welcome back" : "please log in"

Complex Conditions

    let has_license = true

Type Validation

Overview

DSL provides automatic type validation for structured data. When functions return typed values, the runtime validates that the data matches the expected schema.

Automatic Validation

How It Works

When a function declares a return type, DSL automatically validates the result:



type Person {
  name: String
  age: Int
}

def GetPerson() -> Person {
  prompt: "Generate a person"
}

GetPerson()

Validation Process

  1. Function executes and returns a value
  2. Validator checks the value against the declared type
  3. Success: Value passes through with type annotation
  4. Failure: Runtime error with details about what’s wrong

Validation Rules

Rule 1: Required Fields Must Be Present

All fields defined in a type must be present in the value:



type Person {
  name: String
  age: Int
}

{ name: "Alice", age: 30 }

{ name: "Alice" }

Rule 2: Field Types Must Match

Each field’s value must match its declared type:



type Person {
  name: String
  age: Int
}

{ name: "Alice", age: 30 }

{ name: "Alice", age: "thirty" }

Rule 3: Enum Values Must Be Valid

Enum fields must contain one of the defined enum values:



enum Status {
  Pending
  Completed
}

type Task {
  name: String
  status: Status
}

{ name: "Task 1", status: "Pending" }
{ name: "Task 2", status: "pending" }

{ name: "Task 3", status: "Unknown" }

Rule 4: List Elements Must Match Type

For list fields, all elements must match the element type:



type Article {
  tags: [String]
  scores: [Int]
}

{ tags: ["tech", "ai"], scores: [85, 92, 78] }

{ tags: ["tech"], scores: [85, "ninety"] }

Rule 5: Nested Types Must Be Valid

Nested type fields must themselves be valid instances:



type Address {
  street: String
  city: String
}

type Person {
  name: String
  address: Address
}

{
  name: "Alice",
  address: { street: "123 Main St", city: "NYC" }
}

{
  name: "Alice",
  address: { street: "123 Main St" }
}

Type Coercion

Automatic Coercion

DSL attempts to coerce values to the expected type when possible:



type Person {
  name: String
  age: Int
}

{ name: "Alice", age: "30" }

type Product { price: Float }
{ price: 10 }

When Coercion Fails

If coercion is not possible, validation fails:



type Person {
  name: String
  age: Int
}

{ name: "Alice", age: "thirty" }

BAML Integration

Overview

DSL types are automatically converted to BAML schemas for LLM prompts. This ensures LLM responses match your expected data structure without manual schema writing.

BAML (Basically A Markup Language) is the schema format used by the simplify_baml library to communicate type information to LLMs.

How It Works

The Flow

DSL Type Definition
       ↓
  BAML Schema Generation
       ↓
  Included in LLM Prompt
       ↓
  LLM Response (JSON)
       ↓
  Parsed into DSL Value
       ↓
  Type Validation

Example

Your DSL Type:



type BlogPost {
  title: String
  summary: String
  keywords: [String]
}

Generated BAML Schema (sent to LLM):

Answer in JSON using this schema:
{
  title: string,
  summary: string,
  keywords: string[]
}

LLM Response (JSON):

{
  "title": "Understanding AI",
  "summary": "An introduction to artificial intelligence",
  "keywords": ["AI", "machine learning", "deep learning"]
}

Parsed DSL Value:

{
  title: "Understanding AI",
  summary: "An introduction to artificial intelligence",
  keywords: ["AI", "machine learning", "deep learning"]
} : BlogPost

Sequential Workflows

Sequential workflows chain operations together, where the output of each step becomes the input to the next. DSL uses the pipeline operator |> for sequential composition.

The Pipeline Operator (|>)

Concept

The |> operator chains operations, passing the result of each step to the next. Think of it like Unix pipes:

# Unix pipes
cat file.txt | grep "keyword" | sort | uniq

LoadFile("file.txt") |> Filter(_) |> Sort(_) |> Unique(_)

Basic Usage

"hello" |> Upper(_)

"hello" |> Upper(_) |> Length(_)

5 |> _ * 2 |> _ + 3

The Underscore Variable (_)

The _ variable always contains the result of the previous step in a pipeline:

[1, 2, 3, 4, 5] |> Length(_)

"test" |> Upper(_) |> Length(_)

[1, 2, 3] |> map(_, fn x => x * 2 end) |> Sum(_)

Explicit Access

[1, 2, 3, 4] |> filter(_, fn x => x % 2 == 0 end)

10 |> _ * 2 |> _ + 5 |> _ / 3

Variable Binding with as

Bind intermediate results to named variables for clarity and reuse:

["a", "b", "c"] |> Join(_, "-") as joined |> Upper(joined)

5 |> _ * 2 as doubled |> doubled + 3

[1, 2, 3, 4, 5]
  |> filter(_, fn x => x % 2 == 0 end) as evens
  |> map(evens, fn x => x * x end) as squares
  |> Sum(squares)

Parallel Workflows

Parallel workflows execute multiple operations concurrently, allowing independent tasks to run simultaneously. DSL uses the Par() function for parallel composition.

The Par() Function

Signature: (...expressions) -> List

Execute multiple expressions in parallel and return results as a list.

Par(5, 10, 15)

Par(
  Calculate(dataA),
  Calculate(dataB),
  Calculate(dataC)
)

How It Works

  1. All arguments to Par() start executing immediately
  2. Execution happens concurrently (not sequentially)
  3. Par() waits for all operations to complete
  4. Results are returned as a list in argument order

Sequential vs Parallel

Sequential Execution

Operations run one after another:

def main() {
    let resultA = FetchData("endpoint-a")
    let resultB = FetchData("endpoint-b")
    let resultC = FetchData("endpoint-c")
}
main()

Timeline:

[A........] [B........] [C........]
Total: 3x time

Parallel Execution

Operations run concurrently:

Par(
  FetchData("endpoint-a"),
  FetchData("endpoint-b"),
  FetchData("endpoint-c")
) as [resultA, resultB, resultC]

Timeline:

[A........]
[B........]
[C........]
Total: 1x time (if all take same time)

Variable Binding

Bind to List

Par(5, 10, 15) as numbers
numbers

Destructure Results

Par(
  GetUser(1),
  GetUser(2),
  GetUser(3)
) as [alice, bob, charlie]

alice.name

Named Results

Par(
  FetchUsers(),
  FetchProducts(),
  FetchOrders()
) as [users, products, orders]

users |> Length(_)

Workflow Patterns

Common patterns for building robust, maintainable workflows in DSL. Learn when to use sequential, parallel, or mixed approaches for different problem types.

Data Pipeline Patterns

Extract-Transform-Load (ETL)

Classic data processing pattern: extract from source, transform data, load to destination.

def ETLPipeline(sourceFile, destFile) {
  SQL("SELECT * FROM '" + sourceFile + "'") as rawData

    |> filter(_, fn row => row.valid end) as validRows
    |> map(validRows, fn row => {
         id: row.id,
         value: ToFloat(row.value end),
         category: Lower(Trim(row.category)),
         timestamp: row.created_at
       }) as transformed

    |> SaveData(destFile, transformed)

ETLPipeline("input.csv", "output.csv")

When to Use:

  • Batch data processing
  • Data migration
  • Report generation
  • Data warehouse loading

Streaming Pipeline

Process data continuously in small batches:

def StreamProcess(dataStream) { dataStream }
    |> Chunk(_, 10) as batches
    |> map(batches, fn batch => batch
           |> Filter(_, isValid end)
           |> Map(_, transform)
           |> ProcessBatch(_))
    |> Flatten(_)

When to Use:

  • Real-time data processing
  • Large datasets (won’t fit in memory)
  • Continuous data flow

Map-Reduce

Parallel processing with aggregation:

def MapReduce(data, mapFunc, reduceFunc, initialValue) {
  data
    |> Chunk(_, 100) as chunks
    |> Take(chunks, 5) as batches
    |> _ as _ |> Par(
         ...map(batches, fn chunk => Map(chunk, mapFunc end))
       ) as mapped

    |> Flatten(mapped)
    |> Reduce(_, initialValue, reduceFunc)

MapReduce(
  documents,
  fn doc => Length(Split(doc.text, " " end)),
  def (sum, count) := sum + count,
  0
)

When to Use:

  • Large-scale data processing
  • Aggregations over big datasets
  • Distributed computation

Validation Patterns

Validate-Process-Format

Ensure data quality throughout:

def ValidateProcessFormat(input) {
  input
    |> ValidateInput(_) as validated
    |> _ as _ |> Length(validated) == 0
       ? Error("No valid input data")
       : validated

    |> Map(_, transform) as processed

    |> ValidateOutput(_) as validOutput

    |> FormatResults(validOutput)

def ValidateInput(data) { filter(data, fn item => item.id != null && }
    Length(item.name end) > 0 &&
    item.value >= 0)

def ValidateOutput(data) { filter(data, fn item => item.result != null && }
    item.status == "success" end)

When to Use:

  • Data quality critical
  • Multiple processing steps
  • Need to catch errors early

Progressive Validation

def ProgressiveValidation(data) { data }

Anti-Patterns

Anti-Pattern 1: Unnecessary Parallelization

Bad:

Par(
  Length([1, 2, 3]),
  Sum([1, 2, 3]),
  First([1, 2, 3])
)

Good:

def main() {
    let len = Length([1, 2, 3])
    let sum = Sum([1, 2, 3])
    let first = First([1, 2, 3])
}
main()

Why Bad: Parallel overhead exceeds time saved.

Anti-Pattern 2: Sequential Dependent Data

Bad:

def main() {
    let dataA = FetchData("a")
    let dataB = FetchData("b")
    let dataC = CombineData(dataA, dataB)
}
main()

Good:

Par(
  FetchData("a"),
  FetchData("b")
) as [dataA, dataB]

let dataC = CombineData(dataA, dataB)

Why Bad: Wastes time when operations could run in parallel.

Anti-Pattern 3: Nested Pipeline Chaos

Bad:

ProcessData(
  TransformData(
    FilterData(
      LoadData("file.csv")
    )
  )
)

Good:

LoadData("file.csv")
  |> FilterData(_)
  |> TransformData(_)
  |> ProcessData(_)

Why Bad: Hard to read and debug.

Anti-Pattern 4: Ignored Intermediate Results

Bad:

data
  |> Process1(_)
  |> Process2(_)
  |> Process3(_)

Good:

data
  |> Process1(_) as step1
  |> _ as _ |> Log("After step 1: " + ToString(Length(step1)))
  |> Process2(step1) as step2
  |> _ as _ |> Log("After step 2: " + ToString(Length(step2)))
  |> Process3(step2)

Why Bad: Hard to debug when something goes wrong.

Anti-Pattern 5: Over-Parallelization

Bad:

Par(
  ...Map(Range(1, 10001), FetchData)
)

Good:

def ProcessInBatches(ids, batchSize) { ids }
    |> Chunk(_, batchSize)
    |> map(_, fn batch => Par(...Map(batch, FetchData end))
           |> Flatten(_))
    |> Flatten(_)

ProcessInBatches(Range(1, 10001), 10)

Why Bad: Overwhelms system resources.

Anti-Pattern 6: No Error Handling

Bad:

data
  |> Map(_, riskyOperation)
  |> Process(_)

Good:

data
  |> map(_, fn item => {
       ...item,
       result: riskyOperation(item end) ?? null,
       failed: riskyOperation(item) == null
     })
  |> filter(_, fn item => Not(item.failed end))
  |> map(_, fn item => item.result end)
  |> Process(_)

Why Bad: One failure breaks entire pipeline.

Anti-Pattern 7: Repeated Expensive Calls

Bad:

users
  |> filter(_, fn u => IsValidUser(u, GetConfig( end)))
  |> map(_, fn u => ProcessUser(u, GetConfig( end)))
  |> Sort(_, fn u => ScoreUser(u, GetConfig( end)))

Good:

let config = GetConfig()

users
  |> filter(_, fn u => IsValidUser(u, config end))
  |> map(_, fn u => ProcessUser(u, config end))
  |> Sort(_, fn u => ScoreUser(u, config end))

Why Bad: Unnecessary repeated work.

Anti-Pattern 8: Monolithic Functions

Bad:

def ProcessEverything(data) {
  ...

Good:

def ProcessEverything(data) { data }
    |> Validate(_) as validated
    |> Transform(validated) as transformed
    |> Enrich(transformed) as enriched
    |> Format(enriched)

def Validate(data) { ... }
def Transform(data) { ... }
def Enrich(data) { ... }
def Format(data) { ... }

Why Bad: Hard to maintain and test.

Composition Patterns

Pattern Composition

Combine patterns for complex workflows:

def ComplexWorkflow(input) {
  input
    |> Extract(_) as raw
    |> Transform(raw) as transformed

    |> Chunk(transformed, 100) as chunks
    |> _ as _ |> Par(
         ...Map(Take(chunks, 5), ProcessChunk)

    |> Flatten(processed) as flattened
    |> Reduce(flattened, initialState, aggregateFunc) as aggregated

    |> ValidateOutput(aggregated) as validated
    |> FormatOutput(validated)

Layered Architecture

Separate concerns into layers:

def LoadUsers() { SQL("SELECT * FROM users") }
def LoadOrders() { SQL("SELECT * FROM orders") }

def ProcessUsers(users) { users }
    |> Filter(_, isActive)
    |> Map(_, enrichUser)

def ProcessOrders(orders, users) { orders }
    |> Filter(_, isValid)
    |> map(_, fn o => AttachUser(o, users end))

def FullPipeline() {
    Par(
    LoadUsers(),
    LoadOrders()
  ) as [users, orders]

  let processedUsers = ProcessUsers(users)
  let processedOrders = ProcessOrders(orders, processedUsers)

  {
    users: processedUsers,
    orders: processedOrders
  }

Troubleshooting

Command Not Found

Problem: dsl: command not found

Solutions:

  • Ensure DSL is installed: which dsl
  • Add to PATH: export PATH="$HOME/.dsl/bin:$PATH"
  • Reinstall: curl -sSL https://dsl-lang.org/install.sh | sh

Permission Denied

Problem: Permission denied when running scripts

Solutions:

  • Make executable: chmod +x script.dsl
  • Check shebang: #!/usr/bin/env dsl run
  • Run with dsl: dsl run script.dsl

Stdin Not Working

Problem: dsl -c hangs or doesn’t read input

Solutions:

  • Verify piping: echo "5 + 3" | dsl -c
  • Check for interactive prompts (not supported in -c mode)
  • Use heredoc for multi-line: dsl -c <<EOF ... EOF

Trace File Too Large

Problem: Trace output is huge

Solutions:

  • Filter by type: --trace-filter FunctionCall
  • Set minimum duration: --trace-min-duration 1000
  • Disable verbose: remove --trace-verbose

Known Issues

This page documents known limitations and issues in the current version of the DSL.

Language Features

Comments Not Fully Implemented

Issue: Comments are partially parsed but not fully supported.

Impact:

  • Single-line comments (// and #) may be parsed but could cause unexpected behavior
  • Multi-line comments (/* */) will cause parser errors
  • Comments in code may lead to runtime issues

Workaround:

  • Avoid using comments in DSL code until this feature is fully implemented
  • Use descriptive variable names instead of inline comments
  • Document code in external files or markdown

Status: Planned for future release

If/Else Blocks Not Supported

Issue: Traditional if/else block syntax does not exist in the DSL.

Impact:

  • Code using if condition { } else { } syntax will fail to parse

Workaround:

  • Use ternary operator: condition ? then_expr : else_expr
  • Use match expressions for complex conditionals
  • See Control Flow for correct syntax

Status: Ternary and match expressions are fully supported

Syntax Requirements

Pipeline Operator Requires Underscore

Issue: Pipeline operator |> requires explicit underscore placeholder.

Incorrect:

value |> Function

Correct:

value |> Function(_)

Status: Working as designed

Lambda Syntax

Issue: Only fn x => expr end syntax is supported for lambdas.

Incorrect:

fun(x) { x * 2 }

Correct:

fn x => x * 2 end

Status: Working as designed
